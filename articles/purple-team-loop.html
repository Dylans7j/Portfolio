The purple team loop: a red finding is only half an answer

Status

Purple team work fails in a predictable way: the attack gets written up, the rule gets written, and nobody ever checks whether the rule fires on the attack or stays quiet on a normal Tuesday. This article is the check. Every artifact below carries an explicit state.

Artifact What it is Status
Attack chain — broadcast name resolution to NTLM relay Simulated in an isolated lab network against a member server Documented
Telemetry map Which event each attack step would have to create, and which ones Windows does not create at all Documented

Splunk SPL and Sentinel KQL Same behaviors expressed for the two SIEMs I work in Authored · logic reviewed

Coverage matrix Technique to event to rule, with gaps named Maintained

Two of those rows are honest gaps, not finished work. I would rather publish a status table that says "not yet executed" than a detection library that implies coverage it has never demonstrated.

Why the loop

Red work proves I can reach a host. Blue work proves I can see a host. Neither one shows the thing employers actually pay for, which is the connection between them: the moment an attack technique changes the detection, and the detection changes the next attack.

That sounds abstract until you do it once. On the first chain below, the attack succeeded and the detection I expected to fire did not exist, because the event I assumed Windows recorded is generated on the attacker's host, not the victim's. No amount of tuning fixes a rule watching the wrong side of the wire. The loop is what surfaced that, and the loop is what I now run every time instead of writing rules from imagination.

The detection you can't source telemetry for isn't a detection. It's a hypothesis with YAML syntax.

The six steps

  1. Reproduce from notes, not memory. Re-run the chain using the written walkthrough. Record start time, end time, source host, destination host, and the exact command for each step. If I can't reproduce it, I can't test a rule against it.
  2. Map telemetry before writing logic. For each step, ask: which event ID, on which host, in which log, with which field? Write down the answer. Where the answer is "none", that is a visibility gap and it is more valuable than the rule.
  3. Author the logic against the event. Sigma first, because it forces me to name the log source and the field instead of reaching for whatever my SIEM happens to call it. Then translate to SPL and KQL.
  4. Test the positive. Does it fire on the reproduced chain, once, with the fields I can actually triage on?
  5. Test the negative. Does it stay quiet during normal administrative activity? This step kills most rules, and skipping it is why detection libraries rot.
  6. Hand it back to red. What is the cheapest change an attacker makes to get around this rule? Then revise. The revision is the deliverable.

Steps 2 and 5 are the ones people skip. Step 2 is where the real finding lives. Step 5 is the difference between a rule that survives a week in production and a rule that gets muted on day two.

Case one: broadcast name resolution poisoning

This is the chain behind the LLMNR / NBT-NS case on my projects page. A victim needs to resolve a name, the DNS query fails, Windows falls back to a broadcast, and whoever answers first gets an NTLM authentication attempt from the victim. That authentication can be captured to crack offline, or relayed to another host.

Attack view

  • Victim attempts to resolve a hostname that does not exist in DNS.
  • Victim broadcasts on LLMNR (UDP 5355) and NBT-NS (UDP 137).
  • Attacker host answers the broadcast, claiming the name.
  • Victim opens SMB to the attacker and sends an NTLM negotiation.
  • Attacker cracks the challenge response, or relays it to a target that does not enforce SMB signing.

Telemetry map

Step What would record it Reality
Victim broadcast query Sysmon Event ID 22 (DnsQuery) if DNS client auditing is on; otherwise only a network sensor Partial — Sysmon 22 does not reliably capture LLMNR/NBT-NS fallbacks on every build
Attacker answer Zeek dns.log / Suricata, or full packet capture Gap in my lab — no passive sensor in the path yet
Victim connects to attacker on 445 Sysmon Event ID 3 (NetworkConnect), or Security 5156 Available
NTLM authentication arriving at the attacker Security 4624 on the attacker's host Effectively absent — attacker hosts do not forward logs
Relayed authentication at the target Security 4624, logon type 3, NTLM package Available — this is the detection surface

The last row is the useful one. I cannot see the poison, but I can see the authentication that arrives because of it, at the host that receives it. A workstation-to-server NTLM network logon is not normal in a domain that has moved to Kerberos, and it is exactly what a relay produces.

Detection A — NTLM network logon to a member server

title: NTLM Network Logon to Member Server from Workstation
status: experimental
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 3
    AuthenticationPackageName: NTLM
  filter_machine_account:
    TargetUserName|endswith: '$'
  condition: selection and not filter_machine_account
falsepositives:
  - Legacy file shares, NAS appliances and printers that only speak NTLM
  - Workgroup-joined hosts inside an otherwise domain-joined estate
level: medium
tags:
  - attack.lateral_movement
  - attack.t1557.001
  - attack.t1550.002

Deliberately no DC exclusion in the rule body. Excluding domain controllers by hostname is the fragile version of this rule and it breaks the first time a DC is renamed or a new one is promoted. If the environment needs that scope, it belongs in an asset-role lookup or a watchlist join, not in a hardcoded string list.

Detection B — broadcast resolution fallback burst

title: Burst of Single-Label DNS Queries from One Host
status: experimental
logsource:
  category: dns_query
detection:
  selection:
    QueryName|re: '^[A-Za-z0-9_-]{3,20}$'
  condition: selection | count() by Computer, QueryName > 15

Status: authored, not validated. The aggregation syntax above is Sigma's correlation-style counting and needs compiling for the target backend — in Splunk and Sentinel I express it as stats / summarize instead. And the underlying event is only as good as the sensor: without Zeek or a host actually emitting Sysmon 22 for fallback queries, this rule has nothing to count. I include it as the shape of the detection I want, not as coverage I can claim.

Splunk hunt for the relay surface

index=wineventlog sourcetype="WinEventLog:Security" EventCode=4624 Logon_Type=3 Authentication_Package=NTLM
| eval src=coalesce(Source_Network_Address, IpAddress)
| where NOT match(Account_Name, "\$$")
| stats count dc(src) AS sources values(Workstation_Name) AS workstations
        BY ComputerName, Account_Name
| where sources > 2
| sort - sources

Two or more distinct sources authenticating with NTLM to the same account on the same server in one window is the shape of a relay, not of a user at a desk. The threshold is intentionally low because the baseline in a Kerberos-only estate should be near zero — which is a claim I have to measure before I trust it, and the reason the benign run is still listed as pending.

What actually removes the technique

Detection is the consolation prize here. The fix is configuration: disable LLMNR through Group Policy (EnableMulticast=0), disable NBT-NS on adapters, enforce SMB signing and Extended Protection for Authentication so a relay has nothing to authenticate to, and stop allowing SMB between workstation subnets. A detection that fires while the technique still works is a monitoring success and a security failure at the same time, and both belong in the report.

Case two: from prompt to shell

The second chain is the one I care about more, because it is where most blue teams currently have no coverage at all: a tool-capable LLM agent that can execute commands. Injecting the model is step one; the interesting part for a defender is that the agent's runtime, not a person, becomes the parent process of a shell.

Attack view

  • Untrusted text reaches the model as context — a document, a web page, a tool result.
  • The injected instruction causes the agent to call a tool that executes a command.
  • The runtime spawns a shell or an interpreter as a child process.
  • Egress follows: a download, a callback, or a staged payload.

Telemetry map

Step Event Why it matters
Prompt reaches the model Application or proxy logs; WAF body inspection if the agent is HTTP-facing The only place the injection itself is visible
Tool call executes Application log, if the agent logs tool invocations Usually the missing link — most agent frameworks log to stdout only
Shell spawned Sysmon Event ID 1 or Security 4688 with command line Highest-signal event: a web/app runtime becoming the parent of bash or PowerShell
Payload dropped Sysmon Event ID 11 in temp or app directories Corroborates intent when the command line is obfuscated
Egress Sysmon Event ID 3, proxy logs, DNS Distinguishes a failed injection from a successful one

Detection C — interpreter spawned by an agent runtime

title: Shell Spawned by LLM Agent Runtime
status: experimental
logsource:
  category: process_creation
  product: windows
detection:
  parent:
    ParentImage|endswith:
      - '\node.exe'
      - '\python.exe'
      - '\python3.exe'
  child:
    Image|endswith:
      - '\cmd.exe'
      - '\powershell.exe'
      - '\bash.exe'
      - '\wsl.exe'
  suspicious_cli:
    CommandLine|contains:
      - '/dev/tcp/'
      - 'curl '
      - 'wget '
      - 'base64 -d'
      - 'Invoke-WebRequest'
      - 'DownloadString'
  condition: parent and child and suspicious_cli
falsepositives:
  - Developer workstations running agents against a local sandbox
  - CI runners where node legitimately shells out to a build tool
level: high
tags:
  - attack.execution
  - attack.t1059.001
  - attack.t1059.004
  - attack.t1105

The parent-process condition is the whole rule. "PowerShell ran" is noise; "PowerShell ran as a child of the agent runtime with a download cradle in the command line" is a finding. The same logic ports to Linux by swapping the parent images for the service user and keeping the child list.

Sentinel KQL for the same behavior

DeviceProcessEvents
| where InitiatingProcessFileName in~ ("node.exe","python.exe","python3.exe")
| where FileName in~ ("cmd.exe","powershell.exe","bash.exe","wsl.exe")
| where ProcessCommandLine has_any ("/dev/tcp/","curl ","wget ","base64 -d","Invoke-WebRequest","DownloadString")
| project Timestamp, DeviceName, AccountName, InitiatingProcessFileName, FileName, ProcessCommandLine

On the prevention side there is a compensating control worth naming: inspecting inbound content for instruction-shaped patterns at the edge, before it ever reaches the model. It is a filter, not a detection — it raises the cost of the attack and produces nothing in the SIEM. I treat it as one layer, never as the answer.

What makes a rule survive

Four tests, in this order. A rule that fails any of them is a draft.

Test Question Failure looks like
Positive Does it fire once, on the reproduced chain, with fields I can triage on? Fires but only shows a hostname and no user — untriageable
Variant Does it still fire when the attacker changes one thing — PowerShell instead of bash, a different download tool, an encoded command? The rule names a single tool instead of a behavior
Benign Does it stay quiet during patching, backup, admin scripts and onboarding? Fires 400 times a day and gets muted by lunchtime
Scale Would it still be readable if the estate were 50 times larger? Every alert needs one analyst-hour of context rebuilding

The variant test is where Sigma earns its place. Writing the logic against T1059 behavior rather than against a specific binary is what makes a rule survive the attacker's first adjustment — and it is also what makes the false-positive surface bigger, which is why the benign test comes right after it.

False-positive budget

Every exclusion is a hole with a comment attached. I write them as narrowly as the evidence allows and record why, so the next analyst can tell a considered exclusion from a lazy one.

Rule Expected benign source Tuning lever Cost of over-tuning
NTLM network logon to member server NAS, printers scanning to SMB, legacy line-of-business app Whitelist by destination asset + protocol, not by source IP Excluding the source means the relay just moves to that host
Broadcast resolution burst Printer discovery, WS-Discovery, legacy NetBIOS apps Require the queried name to be unresolvable, and the same name from multiple hosts Excluding known names loses the exact behavior being hunted
Shell spawned by agent runtime Developer sandboxes, CI build steps Scope to servers running the agent service, exclude interactive dev sessions Excluding the whole parent path lets the agent do anything it wants

None of these exclusions are applied yet. They are the levers I would pull after measuring the baseline, which is the correct order and the one I keep having to defend to myself when I want to ship a rule faster.

Handing it back to red

The last step is the one that makes this purple instead of blue with extra steps. I attack my own rule.

  • Use a name that resolves legitimately. Register the hostname in DNS and the broadcast never happens — Detection B is bypassed, Detection A still has to catch the authentication.
  • Authenticate with Kerberos instead of NTLM. Detection A is blind by construction. The mitigation is SMB signing, not a better query.
  • Relay to a domain controller instead of a member server. Scoped-out targets are the most common hole in this rule family.
  • For the agent chain, drop the download cradle. A single bash -c with an inline payload never touches curl, so the command-line list in Detection C misses it — the parent-child pair has to carry the rule alone.

Each of those is a rule change, and each one is a sentence I can put in a report: here is what the detection covers, here is what it does not, here is the compensating control for the gap. That is a more useful artifact than a green checkmark.

Next validation step

To move this from authored to validated I need four pieces of evidence, in the same window, from the lab:

  1. Sysmon Event ID 1 from a controlled agent-triggered shell, with the parent chain intact.
  2. Security 4624 logon type 3 with NTLM package on the member server, during the relay test.
  3. Seven days of benign baseline for the same hosts, so the "near zero" assumption is measured instead of asserted.
  4. A Zeek or Suricata capture of the broadcast exchange, which is the only thing that can close Detection B.

When those exist, the status table at the top of this page changes from authored to validated, and the coverage snapshot gains two rows. Until then the honest description of this work is: logic written, structure checked, execution pending.
